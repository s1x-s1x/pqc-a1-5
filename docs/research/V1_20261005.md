# V1: Fixed pid3 FORS Verification

Date: 2026-10-05. This note describes the candidate and its bounded acceptance.
Three independent fixtures passed normal/sanitizer three-path controls in
`validation/incremental-20261005-v1-r1`. Current-engine B1/V1 combined sanitizer
fixtures passed in `release-r1`; historical version differences are recorded in
`EXECUTION_20261005.md`. `isolation-r2` adds 64 complete concurrent requests with
per-request REF results, mixed validity and 16 changed public seeds, using both
shared read-only and private contexts. The actual CUDA build retained scalar
FORS verification and recorded zero V1/A/B candidate hits.

## Mechanism And Scope

The existing `verify_core` recovers one FORS root at a time with scalar F/H.
V1 recovers the six pid3 roots at the same height in one AVX2 package. It uses one
F package followed by 24 H packages. Lane number equals the FORS tree number.
All six roots retain their original order before the existing T_k absorption.
The upper XMSS recovery and final public-root comparison remain in the engine.

The algorithm is the existing SLH-DSA/SPHINCS+ FORS authentication-path recovery,
adapted to the repository's experimental SM3 pid3. The neighboring mechanism is
the existing `thash8_mask` used by WOTS and the signing-side `fors_tree8`; neither
previously performed same-height recovery across the six verification paths.
The implementation claims this specific integration, rather than a new hash
signature construction or a general SIMD invention.

`A15_INCREMENTAL_V1` defaults to 0. Only pid3, SM3, a=24, k=6 and the resolved
AVX2 backend qualify. REF, SHA2, other parameters and CUDA retain scalar FORS
verification. AUTO may qualify after the existing resolver selects AVX2.
There is no public ABI change and no environment-controlled runtime toggle.
Independent REF verification after signing remains the existing scalar path.

## Address And State Contract

The caller supplies the original type-3 FORS work address after digest parsing,
including tree and key-pair fields. For lane i and digest index v_i, the F address
uses absolute index `(i << 24) + v_i` and height 0. H height j+1 uses that absolute
index shifted by j+1. Bit j of v_i selects which child is the current node;
the sibling comes from that tree's j-th signature authentication element.

The helper receives work by value and retains no state. It borrows only the
public signature, parsed indices and public seed midstate. The seed is common
to all lanes. Empty lanes 6 and 7 have an all-zero public address and zero
payload at every stage, including after previous packages produced outputs.
Their outputs are never copied to the six-root result. Only initialized, legal
buffers participate in eight-lane loads.

The logical counters remain six F, 144 H and 150 scalar compression blocks.
The 25 physical packages and 50 padding lane evaluations are separate private
test diagnostics. There are no new heap allocations, locks, queues, shared
mutable request objects or cancellation states. Node and pair buffers are wiped
at helper exit; all input data is public verification material. Compiler
register copies and physical side channels are not covered by that wipe.

## Bounded Acceptance Harness

`test_incremental_v1.c` includes the engine as a standalone test translation
unit. Private diagnostics are gated by `SLH_TEST_BUILD`; release libraries expose
no diagnostic symbol or mutable branch override. Tests require `SLH_COUNTERS`
and AVX2. A CPU without AVX2 returns 77 and proves no new-path acceptance.

The component harness independently constructs compressed address bytes and
hashes the complete public-seed prefix with scalar SM3, avoiding the midstate
final-block constructor and `thash`/`hpair` under test. Its 64 cases cover all-zero,
all-one, alternating and each single-bit index, randomized signature material,
changing public seeds/tree/key-pair fields, left/right decisions at all 24
heights, root order, untouched caller address and output bounds. It checks all
25 stages, absolute tree indices, deterministic padding and exact counters.
Eligibility checks cover seven parameter identifiers and three backends.

Full verification reuses the three existing public pure-mode vectors from
`reference/evidence/python-sm3-128-24.jsonl`; no pid3 signing is needed. A
structured JSON reader extracts only pk, sig, message and context into bounded
binary inputs. Each fixture is checked with REF, existing AVX2 FORS and new V1,
including signature/FORS/WOTS/authentication mutations, public-seed/root,
message/context, signature lengths, context length, NULL arguments and parameter
errors. Status and logical counters must agree, and V1 route hits must be one
for every complete pid3 AVX2 verification and zero for early rejections.

The main build adds a correctness-only target that links the normal support
sources without separately compiling `engine.c`. It must run the harness with
all three fixtures, then run the same target under AddressSanitizer and UBSan.
Existing AVX2 is selected through a test-only thread-local suppression flag;
the flag does not exist in production. No loop timers, cycles, warmup, benchmark
or performance experiment are part of this harness.

## Integration

Include `fors_verify_x8.inc` immediately before `verify_core`, after the existing
hash helpers. Guard a call to `fors_from_sig_x8` with `fors_verify_x8_eligible`.
After the helper, advance the signature cursor by `k*(a+1)*N`; otherwise execute
the unchanged scalar FORS loop. Continue through the existing T_k and XMSS code.
Make the include a real build prerequisite and keep V1 independently selectable
from the A/B hash layout experiments. Passing V1 correctness does not establish
a performance benefit, FIPS 205 SM3 standardization or an overall security proof.
