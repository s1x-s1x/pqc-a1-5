## 3 技术捷径：一个人做得完的六个前提

S 层能压进 102 h，靠的是下面六个技术决定。它们也是报告第 6 章（实现原理与高性能优化）的现成素材，写手 B 可以直接引用这里的数字和理由。

### 3.1 FORS 优先的 SIMD

128-24 默认缓存档 t=12 时，一次签名共 303,112,071 次杂凑调用。其中 FORS 占 301,989,732 次（99.63%），其余 1,122,339 次是 XMSS 子树重算、WOTS 签名和 fors_pkFromSig。

PK.seed‖0^48 恰好是一个 64 字节块，每把密钥只需预压缩一次（midstate）。之后各函数的输入长度与压缩次数如下：

| 调用 | midstate 之后的输入 | 加填充后 | 压缩次数 | 出现在哪里 |
|---|---|---|---|---|
| PRF、F | ADRSc 22 B + 16 B = 38 B | 47 B | 1 | FORS 叶、WOTS 链 |
| H | 22 B + 32 B = 54 B | 63 B | 1 | FORS 与 XMSS 的内部节点 |
| T_k（k=6） | 22 B + 96 B = 118 B | 127 B | 2 | fors_pkFromSig |
| T_len（len=68） | 22 B + 1,088 B = 1,110 B | 1,119 B | 18 | WOTS 公钥压缩 |

所以 FORS 的每一次调用，都是"同一个 midstate + 一个 64 字节块"。8 个通道输入等长，没有分支，也没有长度对齐问题，正是 SIMD 最顺手的形状。S14 只写这一种内核，就覆盖了有缓存签名 99.63% 的调用。

**代价要写清楚。** 密钥生成几乎全是 WOTS 叶：每片叶 273 次调用、290 次压缩，其中 T_len 一次就占 18 次压缩。无缓存签名里，FORS 也只占 20.8%。因此 S 层结束时，R3 的 AVX2 列只有"有缓存签名"一项能体现 8 路收益，密钥生成和无缓存签名基本还是标量速度。这一块由 A5（WOTS x8 与 T_len 流式吸收）补上。写手在第 6、9 章要照实写，不能把 FORS 的加速比套到整个签名上。

内核草图如下，这是内部函数，不进冻结 API：

```c
/* 内部接口，不属于 v2 §4.2 的冻结 API。ctx 内含 PK.seed 的 midstate 与已绑定的 SK.seed */
void sm3_x8_compress1(uint32_t out[8][8], const uint32_t midstate[8], const uint8_t blk[8][64]);
void prf_x8(uint8_t out[8][16], const slh_ctx *ctx, const uint8_t adrsc[8][22]);
void f_x8  (uint8_t out[8][16], const slh_ctx *ctx, const uint8_t adrsc[8][22], const uint8_t in[8][16]);
void h_x8  (uint8_t out[8][16], const slh_ctx *ctx, const uint8_t adrsc[8][22], const uint8_t in[8][32]);
```

**层内批处理。** 一个 z=16 的 FORS 任务自底向上逐层计算，每凑满 8 个同层节点就调用一次 x8 内核。最上面 3 层只有 4、2、1 个节点，走标量，不到任务内调用的十万分之四。

轮函数与消息扩展参考 isa-l_crypto 的 sm3_mb，接口改成"midstate + 单块"。两个老坑照旧要防：SM3 是大端序；填充里的消息长度必须把 midstate 已吸收的 64 字节算进去（乙2）。

### 3.2 子树任务切分

所有并行都走 v2 §4.3 的同一个 `slh_subtree` 接口。OpenMP 只在任务层面并行，任务内部是串行或 x8。

| 场景 | 子树高 z | 任务数 | 每任务叶数 | 主机合并 |
|---|---|---|---|---|
| FORS：6 棵 2^24 叶的树 | 16 | 6 × 256 = 1,536 | 65,536 | 6 × 255 次 H |
| XMSS 无缓存（密钥生成、t=22 签名） | 12 | 1,024 | 4,096 | 1,023 次 H |
| XMSS 有缓存 t=12（只重算目标叶所在的那棵 z=12 子树，再切小） | 8 | 16 | 256 | 15 次 H；上层认证路径取自缓存 |

**参数与实现约束。** `leaf_start` 必须是 2^z 的整数倍；`target` 为 `UINT32_MAX` 时只算根。FORS 的叶索引要加偏移 i·2^a，最大到 6·2^24，所以地址字段一律用 uint32（乙3）。线程数显式设置（乙4）；计数器线程局部，结束时再汇总（乙5）。S10 的验收标准是多线程输出与单线程逐字节相同。

**计数口径的坑。** v2 附录 A.2 的计数公式沿用 FIPS 205 的算法，只算认证路径上的兄弟子树，不算目标叶本身和它到根的路径；子树切分路径则会把整棵树算完。差别是：128-24 每棵 FORS 树多出约 25 次调用，有缓存的 XMSS 子树多出约 285 次，合计约 440 次，占一次签名调用的百万分之一点五左右。

所以 R2 的"逐项相等"只针对 REF 单线程路径。切分路径由 `count.py` 另给一套公式，两套都要对上（S11）。这个差别不先写进 SPEC，深夜对计数时很容易误判成 bug。

### 3.5 一键出表

`make_tables.py` 读取 `bench-out/*.jsonl`、`vectors/MANIFEST`、`count.py` 和 `overuse.py` 的输出，生成可以直接贴进报告的 Markdown 表和 CSV。每张表的表头写明生成时间、git 提交号和"最终 / 非最终"；每个数字附带来源（文件名:行号），写手在门4 逐条追溯时照着查。

**一道防线。** 只要任何一行的 git 字段早于 gate3 标签，脚本就拒绝输出"最终"字样。这样"报告数字全部来自冻结后的代码"就由脚本把关，不靠人记。图由写手 B 用 CSV 画（脚本或 Excel 均可）。

### 3.6 测试里从不签 128-24

128-24 单核标量签一次，有缓存约 65 s，无缓存约 327 s（估算，见附录 C）。所以有四条规定。

单元测试和回归只验签，不签名。128-24 的 fixtures 在 S21 一次性生成，有效期 365 天，not-before 提前一天（丙6），并登记进 MANIFEST。alt 链的开发与调试用 128s（单核签名估算约 0.5 s）或 v9 已有的 ML-DSA-44 快速迭代，全部通过后再换 128-24 的 fixtures 跑一遍。128-24 不允许设为 pq_signer（丙4）。

## 4 正确性与独立性：五层保障

v2 靠甲乙背靠背得到两份独立实现，一人开发做不到。v3 换成五层保障，每层堵一类错误，叠起来的证据强度不低于背靠背。

### 4.1 五层

| 层 | 做法 | 能抓住的错误 | 证据 |
|---|---|---|---|
| 一：不同底座 | C 引擎改自 slhdsa-c，Python 模型改自 fips205.py。两者是不同语言的两套代码库，各自通过了 ACVP | 两份代码结构不同，差分有意义；同一个误解被原样写进两边的概率下降 | §3.3 底座表 |
| 二：小改动、全列出 | 两边的改动都控制在少量函数内，逐函数列进差异清单 | 改动可审，评委能看到改了什么 | 报告附录 E（或支撑材料） |
| 三：外部锚点 | (A) ACVP SHA2-128s/128f 共 1,248 例；(B) SHA2-128-24 对 xous PR #1002；(C) SM3-128s/128f 对 gmsm | 参数通路和杂凑通路分别被外部实现钉住 | R1 |
| 四：写作组逐行审读 | 共两次：10/08 审 SM3 实例化与参数表；10/12 审子树、缓存、OpenMP 与 SIMD。对照 FIPS 205 与 SPEC 逐行核 | 读规范时的误解、常量抄错、边界条件 | 审读记录（写进 LOG.md） |
| 五：随机差分 | 1,000 组玩具参数（pid 201）的随机密钥与消息，C 与 Python 逐字节比；subtree 向量；(D) SM3-128-24 至少 3 组完整的 keygen+sign | 只有组合起来才出现的错误 | R1 |

**写作组怎么审。** 写作组不需要会写 C，只核对四类东西：常量、字节布局（ADRSc、消息编码、OID 的 DER）、循环边界和分支条件。乙3 的五个坑逐条过一遍。开发者提前把要审的函数在差异清单里标出来，每次审读控制在 2 小时以内。

**钳形论证。** (A)(B) 证明参数通路正确，包括 128-24 这一行参数；(C) 证明 SM3 实例化通路正确；(D) 直接核对两者的组合。(D) 的两边虽然出自同一人之手，但前两条钳子分别来自外部实现。一个共模错误要漏网，必须同时骗过外部向量和两套不同的底座。

### 4.2 共模错误与对应防线

| 错误类型 | 例子 | 防线 |
|---|---|---|
| SM3 本身 | 字节序；填充长度没算 midstate 的 64 字节 | GB/T 32905 示例；(C) |
| SM3 实例化 | ADRSc 压缩、midstate、HMAC-SM3、MGF1-SM3 | (C) 对 gmsm |
| 与参数相关的通路 | lg w=2 时校验和移位为 0；base_2b 要支持 b=2；a=24 时累加器宽度不够 | (B) 对 xous 的 SHA2-128-24 |
| d=1 的未定义行为 | idx_tree 位数为 0 时右移 64 位 | (B) 加 UBSan |
| 128-24 参数行抄错 | h、a、k、m 任一写错，两份代码一起错 | pid 3 与 pid 103 共用同一个参数结构体，单元测试断言两者除杂凑标识外完全相同；签名长度 3,856 B 与 R2 公式互相核对；写手 A 对照 ipd 原文 Table 1 逐格核 |
| 子树、缓存、SIMD | 偏移、边界、通道错位 | subtree 向量；(F)；t=0…22 全档；篡改缓存必须返回 SLH_ERR_CACHE |

### 4.3 报告里怎么写

写方法，不写人数。不写"两名队员独立实现"，而写"C 引擎与 Python 参考模型基于不同语言的两套代码库，各自先通过 ACVP，再在其上做小幅改动，改动逐函数列于附录"。外部锚点、随机差分和审读流程，都按 R1 的实际数字如实写。
