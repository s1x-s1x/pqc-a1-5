## A. 最终优化冻结前优先处理

### F01：签名预算的算法别名拆账

**属实，已复现。** [signing_budget.py](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/tools/signing_budget.py:52) 的 key_id 直接包含原始算法字符串；限额选择使用小写，身份计算却保留大小写。[CLI](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/tools/cli.py:106) 使用大写名称，[CA](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/base_tls/tls/alt_chain.py:181) 使用小写名称。

本次在隔离 SQLite 中，以相同 32 B 公钥、同 DB、限额 1，两个实际入口名称分别成功预约一次，总使用量 2；每个完全相同名称的第二次预约均被拒绝。并发控制探针则是 32 请求、限额 7、恰好 7 次成功，失败记录继续收费，表明问题在身份分裂。

建议统一为白名单内稳定 pid/OID 与公钥的身份。迁移现存别名记录时合并已消耗次数及 receipts，保持失败/崩溃预约消耗；不得以迁移重置使用量。验收覆盖 CLI、CA、CPU/CUDA 准备及续跑共用同密钥、同账本、小限额和迁移后的超额拒绝。

证据：[预算及续跑探针](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/build/merged-audit-20261004/budget/results.json)。

### F02：Python ABI 输入长度、整数转换与分配顺序

**属实，已复现。** [_buffer](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/tools/native.py:20) 转换为 bytes，但调用端仍取原对象 len。8 B 的 memoryview('I') 含两个元素，消息和 context 到 ABI 时均只剩 `0102` 两字节。普通 bytes 对照传入完整 8 B。

另复现 threads 为 ±2^32 时到 ABI 成为 0，2^32+1 成为 1；cache level 2^32 成为 0；subtree start/target 2^32 成为 0。z=25 在 C 检查前已分配 400 B auth；真实 C 随后会拒绝该高度，本次没有尝试巨量分配。

建议入口先一次性规范化字节，并全程使用转换后长度；先检查整数类型、范围、后端/叶类型和参数允许高度，再做 ctypes 转换及分配。验收覆盖 bytes/bytearray/类型化 memoryview、pure/internal/prehash/digest、context、整数上下界和无副作用的超范围拒绝。

证据：[ctypes 回调结果](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/build/merged-audit-20261004/native/native-probe-results.json)。真实签名、原生调用和性能样本均为 0。

### F03：CPU/GPU 临时秘密清理不完整

**静态确认。** [engine.c](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/c/src/engine.c:145) 的 work、八路 lanes、线程上下文副本、FORS secret 和 HMAC pad 等含秘密相关内容，缺统一清理。[密钥生成](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/c/src/engine.c:372) 在复制种子至 tmp 后，缓存分配失败直接返回，遗漏 tmp 擦除。

[CUDA](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/c/src/sm3_cuda.cu:63) host job.skseed 未显式擦除，按值 kernel 参数的秘密生命周期未完整定义。RAII 节点缓冲已有 cudaMemset/cudaFree，kernel 已有同步和错误查询；但清零/释放返回状态被忽略，清除节点不等于清除秘密参数。

建议减少含秘密结构的按值复制，建立正常、异常、分配失败和 OpenMP 任务退出的统一 cleanup；明确 CUDA host job、参数及设备工作区的生命周期、清除完成与错误处理。在优化构建中验证显式擦除未被删除，并用专用测试观察预定清除点。已有上下文、随机 seed 和失败签名清理继续保留。

这是内存残留及防护保证缺口；本次未读取进程转储或设备秘密。getrandom 的 EINTR 重试可随可靠性收尾补充，目前该错误会使操作失败。

### F04：C 库缺内部候选签名隔离

**静态确认，与此前审查相同。** [slh_sign_internal](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/c/src/engine.c:384) 直接将调用者 sig 交给 sign_core，再在同一缓冲区自验，失败后清零。现有完整自验、故障码、失败长度 0 和最终清零均有作用，尚未满足“内部候选 → 自验 → 成功复制”的库内发布契约。

Python/CLI 在内部 ctypes 缓冲计算，成功后返回 bytes 或写文件，具有调用层隔离；该行为不覆盖直接 C ABI 使用者。

建议 C 库生成内部候选，统一成功复制与失败清理，pure/internal/prehash/digest 共用这条路径。补候选生成期间外部缓冲保持预定状态、自验失败未发布、输出容量、失败长度及秘密工作区清除检查。若自验独立性需要增强，可显式选择参考恢复路径；当前完整恢复存在，但 WOTS 仍可能共用 AVX2 后端。

### F09：E1 的序列化字节口径混用

**已复现。** [connection.py](C:/Users/23380/Desktop/密码比赛/pqc-a1-5/base_tls/tls/handshake/connection.py:212) 使用 tag_length+5，即21 B。实际 seal 增量为内层类型1 B+tag16 B，即17 B；私有TCP另加4 B长度前缀，合计21 B；标准TLS另加5 B记录头，合计22 B。21 B对私有加密帧恰好正确，但对inprocess加密输出多计4 B，明文消息又未计私有前缀；也未涵盖分片后的逐记录开销。

建议分列 DER、握手消息、当前 harness 实际帧、标准 TLS 记录模型和实际 TCP/IP字节，依据真实序列化输出逐记录计数；预估数据与实测分列。修复后才用于E1、首轮传输量、initcwnd/额外RTT分析。当前不开展网络性能采样。
